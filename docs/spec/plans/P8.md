# P8 plan — Backend and library

## Goals

An invited friend signs in with a magic link, uploads a recording, watches the analysis
progress live, and finds the song in their library with their practice history. A worker
on the owner's machine (`isai worker`) processes the queue. The uploaded audio is deleted
when the job ends, whether it succeeded or failed (rule 8). Everything runs against a
local Supabase stack. Hosting is P9. No Song schema change.

Branch: `p8-backend`, from `p5-arranger` (the stack holds every earlier phase).

## Approval

The owner approved the spec's open items on 2026-11-15:
- **Backend design, as specced:**
  - Supabase
  - a jobs-table queue with leases
  - invite-only magic-link sign-in
  - the `api/` boundary rule
  - Realtime for job progress
- **Dependencies:**
  - `@supabase/supabase-js`
  - `react-router`
  - the Python `supabase` client
  - the Supabase CLI, as a dev dependency in `web/`, run with `pnpm exec supabase`
- **Sharing:** songs are private by default, with a per-song "Share with the group"
  toggle.

**Still needs approval** (this plan):
1. **ADR 0015, backend**, written as step 1 below and `accepted` on approval of this
   plan.
2. **CLAUDE.md:** a new hard rule 10 ("only `web/src/api/` imports supabase-js"), plus
   `supabase/` in the repo layout and the new commands.
3. **Upload sweeper, a change from the spec.** Current Supabase blocks direct SQL deletes
   on `storage.objects` (to be confirmed in step 2), so `pg_cron` can't remove files on
   its own. The split:
   - `pg_cron` runs `requeue_expired()` every minute.
   - `pg_cron` also fails queued jobs whose upload is over 24 h old (`upload_expired`).
   - The worker deletes upload objects over 24 h old through the Storage API, at start-up
     and every 10 minutes. `isai worker sweep` runs it once.
   - If direct deletes turn out to work, `pg_cron` does it all, as specced.
4. **End-to-end test at the API level, not through a browser.** A Vitest suite
   (`pnpm test:e2e`, needs the local stack) drives the same `api/` clients the pages use:
   sign in, upload a synthesised WAV, `isai worker --once`, live progress, song in the
   library, a session saved and listed. The pages get dom tests with fakes, and a manual
   walkthrough with the owner. Playwright, for a real-browser e2e, would be a new
   dependency of several hundred MB of browsers, so it's not proposed.
5. **Local mode stays.** Without `VITE_SUPABASE_URL` the app works as it does today:
   example songs, open a `.song.json` file, sessions in IndexedDB. Tests and offline use
   keep working, and P9 needs only the variables.

**Prerequisite for the owner:** Docker Desktop running, for `supabase start`.

## Design

### Database (`supabase/migrations/`, forward-only)

| Table | Columns beyond the architecture spec §6 |
|---|---|
| `profiles` | `preferences jsonb` (notation only) |
| `invites` | `email citext primary key` |
| `songs` | `level`, `error_code`, `created_at`; `status` is `analysing`, `ready` or `failed` |
| `jobs` | `level`, `title`; `status` adds `waiting_upload` before `queued`; `created_at`, `finished_at` |
| `sessions` | P6's session record: columns for the facts, the result as `jsonb`; `id` bigint identity |

- **Sign-up gate:** a `BEFORE INSERT` trigger on `auth.users` rejects emails missing from
  `invites`. A second trigger creates the profile (`owner` if the invite says so) and
  sets `invites.accepted_at`.
- **RLS:** every table has RLS on.
  - Members read and write their own rows.
  - `songs` with `shared = true` can be read by any signed-in member. Their sessions
    stay private.
  - `jobs`: owners read their own. Nobody but the service role moves `status` past
    `queued`.
- **RPCs:**

  | RPC | Called by | Does |
  |---|---|---|
  | `create_upload(title, source_type, level, ext)` | the user | daily cap (10 per day), the type and extension allowlist; inserts the song and the job (`waiting_upload`); returns the ids and the upload path |
  | `submit_job(job_id)` | the user | checks the object exists in `storage.objects`, then sets `queued` |
  | `queue_position(job_id)` | the user | security definer: how many queued jobs are ahead |
  | `claim_job(worker_id, lease_sec)` | the service role | `FOR UPDATE SKIP LOCKED`; sets the lease |
  | `renew_lease(job_id, worker_id)` | the service role | |
  | `set_stage(job_id, stage)` | the service role | |
  | `finish_job(job_id, summary)` | the service role | fills the song's summary columns and paths; `succeeded` |
  | `fail_job(job_id, code, message)` | the service role | |
  | `requeue_expired()` | `pg_cron` | back to `queued`, at most 2 attempts, then `failed` with `timeout` |

- **Storage:**
  - `uploads`: private, 100 MB, an audio MIME allowlist, users insert only under
    `{uid}/`.
  - `songs`: private, read through 10-minute signed URLs by the owner, or by anyone when
    the song is shared.
- **Realtime:** `jobs` and `songs` are in the `supabase_realtime` publication. RLS
  filters what each user receives.
- **`seed.sql`:** the owner's invite (an `owner`-role invite for a placeholder address
  the owner replaces locally) and one member invite.
- **`supabase/tests/*.sql` (pgTAP):**
  - RLS for two members and a shared song
  - the sign-up gate
  - claim, lease and requeue
  - the daily cap
  - `submit_job` without an object

### Worker (`pipeline/src/isai/worker/`)

| File | Contents |
|---|---|
| `ports.py` | `JobQueue`, `ObjectStore`, `SongRepository` protocols; the `Job` and `Summary` dataclasses |
| `fakes.py` | in-memory versions, used by every worker test |
| `supabase_impl.py` | implementations over the `supabase` client (service role) |
| `errors.py` | pipeline exceptions and exit codes → `decode_failed`, `too_long`, `silent`, `unsupported_type`, `model_failed`, `timeout`, `internal`; each code has a learner message and a next step (shared with the web through `errors.json`) |
| `loop.py` | `process_one(job)` and `run(stop_event)`: claim → download into a temp dir → `pipeline.run` with a per-job cache inside that temp dir (`log_stream` updates `set_stage`) → upload Song JSON and MIDI → `finish_job`. `finally`: delete the upload object and the temp dir (the stems and the cache with it). A lease thread renews every 30 s. A per-job wall-clock timeout (20 min) → `timeout`. SIGINT and SIGTERM finish the current job, then exit. |
| `sweep.py` | expired uploads, as in approval item 3 |

- **CLI:** `isai worker [--once]`, `isai worker sweep`.
- **Config:** `ISAI_SUPABASE_URL`, `ISAI_SUPABASE_SERVICE_KEY`, `ISAI_WORKER_ID`, read
  from the environment or `pipeline/.env` (gitignored).

### Web

| Path | Contents |
|---|---|
| `src/api/` | `types.ts` (the interfaces), `fakes.ts`, and `supabase/`: `AuthClient`, `SongStore` (list, get, signed Song and MIDI URLs, delete, share), `SessionStore` (implements P6's interface), `JobWatcher` (Realtime), `UploadClient`, `PreferencesStore` |
| ESLint | `@supabase/*` imports are banned outside `src/api/`, with a probe test like rule 4's |
| Routing (`react-router`) | `/` library (signed in) or the local example picker; `/sign-in`; `/upload`; `/jobs/:id`; `/songs/:id`; `/songs/:id/practice`; `/songs/:id/results`; `/devices`. The existing pages are reused: `App` becomes a shell, and the song pages take a loaded Song. |
| New pages, following the prototypes and STYLE_GUIDE §6–7 states | `SignIn`, `Library`, `Upload`, `JobProgress`; plus `SongOverview` additions: download MIDI and JSON, delete, share toggle |
| Sessions | signed in, the Supabase store replaces IndexedDB. On first sign-in, local sessions are offered for import (once). |
| Settings | stay per device. Only notation preferences sync, through `profiles.preferences`. |

### Local full stack

- `supabase start` (through `pnpm --dir web db:start`), `pnpm dev`, `uv run isai worker`.
- Documented in the root README, with `.env.example` files for `web/` and `pipeline/`.
- No justfile (it would be a new tool).

## Progress (2026-11-15)

Built in 7 commits on `p8-backend`: ADR 0015 (`4a9fbda`), the database (`e1111a9`), the
worker (`16b5ae0`), the api/ layer and rule 10 guard (`f2b8b8c`), the pages (`f213ddf`),
the end-to-end test (`3e99a26`), and these docs.

Differences from the plan:
- `release_job` RPC added: the second Ctrl+C puts the job back in the queue, and the
  upload stays because the job isn't over. A lost lease also keeps the upload.
- The worker runs `isai analyse` in a child process, so the 20-minute deadline and a
  release can stop it.
- `upload_expired` joins the error codes, for jobs whose upload is over 24 h old.
- A `/devices` route at the top level isn't built: the Devices screen is
  `/songs/:id/devices`, where the keyboard connection lives today.
- `web/.env.example` isn't added: the repo's permission settings block `.env*` files. The
  root README lists the variables instead.

Open for the owner:

  practise, share, delete.
- After a real run, check the Storage dashboard (Studio, `uploads` bucket): empty.
