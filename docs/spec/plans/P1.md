# P1 plan — Playback

## Goals

Open a Song (one of the two examples or a local `.song.json`), press play, hear it on a
sampled piano, and watch a canvas keyboard light the keys in time with the Tone.js
transport. Connect a MIDI keyboard through a `WebMidiInput` adapter and see your notes on
the same keyboard; optionally Isai plays them too. Lint guards and tests enforce rules 4–6
in code. Precompile the Song validator (review #2) and clear the pipeline review tidy-ups
(#3–#8). There's no schema change, and nothing from training or performance mode.

## Files

**Docs:** `docs/adr/0004-audio-engine-and-master-clock.md` (proposed → accepted by you);
`docs/spec/p1-playback.md` (status `ready`); `README.md` (piano samples credit,

**Web — MIDI (`src/midi/`)**
- `AudioClock.ts`: `interface AudioClock { now(): number; fromDomTimestamp(ms: number): number }`.
- `WebMidiInput.ts`: takes a `requestAccess` function (defaults to
  `navigator.requestMIDIAccess`) and an `AudioClock`. Parses status bytes `0x8n`/`0x9n`
  (velocity-0 note-on counts as note-off) and ignores everything else. Errors:
  `MidiUnsupportedError`, `MidiPermissionError`, `MidiDeviceError` (unknown or busy).
- `WebMidiInput.test.ts`: uses a fake `MIDIAccess`/`MIDIInput`.

**Web — audio (`src/audio/`)**
- `types.ts`: interfaces only: `Transport` (`start pause stop seek seconds state
  schedule clear clock`) and `Instrument` (`noteOn noteOff releaseAll loaded`).
- `tone.ts`: the only file that imports `tone`. `createToneAudio()` lazily imports it
  and returns `{ transport, piano }`. The Sampler falls back to a PolySynth on load
  failure, and the clock uses `getOutputTimestamp()`.
- `FakeTransport.ts`, `FakeInstrument.ts`: for tests. `FakeTransport` advances its time
  by hand.

**Web — engine (`src/engine/`)**
- `activeNotes.ts`: `buildNoteIndex(notes)` (sorted by start, plus a running max end)
  and `activeNotesAt(index, t)`, which binary-searches and returns `{ midi, hand }[]`.
- `player.ts`: `createPlayer(song, transport, instrument)` with play, pause, stop and
  seek. It schedules each note's on and off events, and seek or stop clears and
  reschedules them and calls `releaseAll()`.
- Tests: `activeNotes.test.ts`, `player.test.ts` (empty song, single note, overlapping
  notes on the same key, pause/resume, seek mid-note, stop, end of song).

**Web — piano (`src/piano/`)**
- `ranges.ts`: `KEYBOARD_SIZES` (49 C2–C6, 61 C2–C7, 76 E1–G7, 88 A0–C8).
- `layout.ts`: `layoutKeys(range, width)` returns white and black key rectangles, plus
  `outOfRange(notes, range)` giving low and high markers.
- `KeyboardRenderer.ts`: plain TypeScript. It draws one frame into a 2D context
  interface, from the key layout, song notes and held keys (a `Uint8Array(128)` of
  velocities). Token colours are read once with `getComputedStyle`.
- `PianoController.ts`: owns the rAF loop. It subscribes to `MidiInput` (filling the
  held-keys buffer, and playing your notes through the instrument when that's enabled),
  reads `player.seconds` every frame, and updates the position readout through a DOM
  ref. It pauses on `visibilitychange` and cleans up on dispose.
- `Keyboard.tsx`: a canvas and a ref. It creates the controller in `useEffect`. No note
  ever reaches React state.
- Tests: `layout.test.ts`, `KeyboardRenderer.test.ts` (fake context: colours used per
  hand, your notes, out-of-range markers), `PianoController.test.ts` (fake rAF, fake
  MIDI, fake transport).

**Web — theory (`src/theory/`)**
- `pitch.ts` with `midiToName(midi, prefer?)` and `index.ts`. `pitch.test.ts` covers
  0, 21, 60, 108, 127, flats and range errors.

**Web — page**
- `App.tsx`: song picker (`.seg` with the two examples, plus "Open a .song.json file"
  through `<input type=file>` and `parseSong`), transport bar, keyboard size `.seg`, and

  sound failed, and invalid song with a next step.
- `MidiPanel.tsx`: device `.choice` list, "Scan again", connect and disconnect, a
  "Play my notes through Isai" toggle (`aria-pressed`), and the waiting, no keyboards,
  blocked, unsupported and busy states. React state holds only the device list and

- `main.tsx`: the real wiring (`createToneAudio`, `new WebMidiInput(...)`).
- `App.test.tsx`: keeps the server-render checks, adds a jsdom render with fakes, and

**Web — validator and guards**

## Differences from the plan

- **No `@testing-library/react`.** React 19's `act()` with `react-dom/client` was enough for
  the DOM tests, so only `jsdom` was added. That also avoided its `@testing-library/dom`
  peer dependency.
- **Tone runs on a native `AudioContext`.** The `standardized-audio-context` wrapper Tone
  uses has no `getOutputTimestamp()`, so `tone.ts` creates the context and passes it to
  `Tone.setContext`. The MIDI time mapping is unchanged from ADR 0004.
- **`transport.start()` passes the current position.** Without it, Tone would start at 0
  after stop() + seek().
- **The "play my notes" monitor is `engine/monitorMidi`,** not part of `PianoController`.
  It's about sound, not drawing, and is easier to test on its own.
- **The player counts notes per key.** Tone releases every voice of a pitch at once, so the
  end of one note would otherwise cut off an overlapping note on the same key. Velocity-0
  notes light the key but don't sound.
- **ajv standalone:** `ajv-formats` comes in as a named ESM import and `ucs2length` is
  inlined (CJS default-export interop differs between Node and Vite). Any other `require`
  fails generation loudly.
- **Two design-system recipes added:** `.piano-canvas` and `.range` in `components.css`, with
  matching lines in `STYLE_GUIDE.md`. No tokens changed.
- **Pill colours fixed after a browser run.** Song-note pills first used `--hand-right`,
  which in the dark theme is the same grey as `--piano-white`. Right-hand notes were
  invisible on white keys. They now use `--piano-pill-*` with a `--piano-pill-edge`
  outline, as in the Practice prototype, and the theme observer is gone because piano
  tokens never theme.
- **The CLI exits 3 for a missing schema**, separate from exit 2 for a missing input.

## Risks

- **ajv standalone ESM** may emit `require` calls; the gen script rewrites them, and a
  test covers the result. If that turns out fragile, the fallback is to keep the runtime
  compiler and record #2 as slipped.
- **`new Function` in Tone.js.** If the built chunk contains it, I'll find the cause and
  record it here rather than patch around it.
- **jsdom has no canvas.** `getContext` returns null, so the controller tolerates a
  missing context, and the renderer is tested on a fake context instead.
