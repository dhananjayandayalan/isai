# P9 plan — Deployment and operations (repo side)

## Goals

Everything production needs that lives in the repo, so that going live is the owner
choosing hosts, a budget and a domain, adding secrets, and pressing deploy. Nothing is
deployed, and no paid service, account or production key is touched, in this round.

Branch: `p9-deploy`, from `p8-backend`.

## Approval

On 2026-11-15 the owner chose "prepare, don't deploy" and gave the go-ahead. Still the
owner's call, and not started until they decide:
- **ADR 0016, hosting:** written as `proposed` with a recommendation.
- the monthly budget and plan tiers
- the domain
- the GitHub repo and its environments, plus the CI secrets
- every exit criterion that needs production: the deploy, the friend test, the alert
  test on prod, the restore drill, the production audit

No new runtime dependencies. CI uses GitHub Actions; the worker image uses public base
images.

## Tests

- **pgTAP:**
  - heartbeats: only the service role writes them; anyone signed in can ask whether a
    worker is alive
  - `client_errors`: insert only, and the rate limit
  - `admin_stats` and `ops_alerts`: the owner only, the service role only
  - `delete_my_account`
- **Worker:** heartbeat writes with fakes; `isai admin check`, `delete-user` and `backup`
  against fakes, with one slow test on the local stack.
- **Web:**
  - the offline banner
  - the Admin page (owner only; its states)
  - the About page
  - account deletion
  - the error reporter (rate limit, no PII)
  - `hosting.mjs` output (CSP and headers) and the samples lock check, unit tested
- **CI:** can't run without a GitHub remote. The workflows are checked for syntax
  (`actionlint` through Docker if available) and every step's command runs locally.

## Exit criteria (from the spec)

Everything the repo can do is built and tested locally. What's left needs the owner's
accounts, keys or production.

- [ ] Hosting ADR accepted; budget approved; secrets in place (owner: ADR 0016 is `proposed`; setup list in `docs/runbooks/README.md`)
- [ ] CI runs every check above on PRs and blocks merges on failure; a deliberate rule-4 probe in a PR fails CI (workflows written and actionlint-clean; every step runs locally; needs the GitHub repo and branch protection)
- [ ] Production web on the custom domain; security headers verified (no CSP violations while practising, uploading and calibrating) (`build:site` writes the headers, unit tested; the browser check is on production)
- [ ] Samples served from our own path; the third-party sample host is no longer contacted (built and checked against the lock locally; verify on production)
- [ ] A friend (not the owner) signs in, uploads, practises and sees results on production
- [ ] Worker offline → the UI says so; worker back → the queue drains (heartbeat, `worker_online()` and the notice built and tested: pgTAP, DOM tests, e2e; repeat on production)
- [ ] Alerts fire in a test (a forced job failure; the worker stopped) (`ops_alerts()` pgTAP-tested, `isai admin check` exits 1; the GitHub email needs the repo)
- [ ] Restore drill done and recorded; account deletion tested (local drill done and logged; account deletion tested in pgTAP, DOM and e2e; the staging drill is the owner's)
- [ ] Rule 8 audit query on production: zero `uploads` objects older than 24 h, and no audio types in the `songs` bucket (in `ops_alerts()`, so `isai admin check` and the watch run it; all clear locally)
- [x] Runbooks written for every item listed (`docs/runbooks/`)

Differences from the plan:
- **Worker image base:** `python:3.11-slim`, not a CUDA image. torch's cu130 wheels bring
  their own CUDA runtime, and the host supplies the driver.
- **Restore** needs a target with the migrations applied. The dump writes
  `INSERT ... ON CONFLICT DO NOTHING`, so seeded rows don't clash, and the restore runs in one
  transaction with triggers off.
- **`ISAI_DATABASE_URL`** is documented in the READMEs, not in `pipeline/.env.example`
  (this repo's permission settings block reading `.env*` files).
